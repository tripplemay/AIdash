# ADR-004: AIGC 内容生成链路工程化经验总结

> 记录时间：2026-03-18
> 适用范围：所有涉及 AI 生成内容（AIGC）的业务系统
> 来源项目：AI Dash 智能课程系统 — 课程研发模块

---

## 一、背景

AI Dash 的课程研发模块使用 AI（大语言模型 + 图片生成模型）驱动课程设计全流程：框架生成、课次方案、图片封面、内容审核。系统上线后，通过持续的生产环境验证，发现了大量 prompt 组装、模板管理、图片生成链路中的隐蔽问题。

这些问题的共同特征是：**代码逻辑没有报错，AI 也返回了结果，但生成质量不符合预期**。传统的单元测试和集成测试无法捕获这类问题，因为"prompt 是否完整"不是二元判断，而是一个连续光谱。

本文档将完整排查过程中的发现、分析、解决方案和最终架构沉淀为可复用的经验。

---

## 二、核心教训

### 教训 1：AIGC 系统的质量问题是隐性的

传统 bug 会报错、会崩溃、会显示空白。但 AIGC 的 bug 表现为"生成了，但不够好"：
- 少注入了一段基线，课程方案不够专业，但"看起来还行"
- 图片 prompt 缺了年龄段信息，6 岁和 15 岁的课程封面画风一样
- 历史修改意见累积到 prompt 中，图片越改越偏，但每次都能出图

**经验**：AIGC 系统需要建立 prompt 可观测性（审计日志），而不是依赖"结果看起来对不对"来判断。

### 教训 2：Prompt 的"最终组装态"才是真相

一个 prompt 的最终内容可能来自 5-6 个不同的源头：
- 数据库模板（管理员配置）
- 模板变量替换（项目属性、标签）
- 基线文档注入（课程设计约束）
- 硬编码回退（代码中的默认 prompt）
- 用户输入（反馈意见、自定义描述）
- 运行时拼接（构图引导、风格前缀、年龄提示）

任何一层缺失或错位，AI 收到的就不是完整的指令。但开发者看代码觉得"每层都有"，实际运行时可能因为 DB 模板存在导致硬编码回退不执行、基线文件改名导致加载为空、变量名不匹配导致替换为"未指定"。

**经验**：必须记录和审查"AI 实际收到的完整 prompt"，而不是"代码中写的 prompt"。

### 教训 3：图片生成比文本生成更容易出错

文本生成有 system prompt + user message 的结构化分离，模板系统天然适配。但图片生成的 prompt 是一段扁平的描述词，需要手动拼接多个层次：
- 构图引导（全局约束）
- 年龄段提示（受众适配）
- 风格前缀（视觉风格）
- 内容描述（AI 生成的场景描述）
- 用户修改意见（增量要求）

每个层次有不同的来源、不同的更新时机、不同的适用范围。遗漏任何一层都不会报错，只会让图片"不够好"。

**经验**：图片 prompt 的组装逻辑需要和文本 prompt 同等重视，统一管理，统一审计。

## 三、问题发现过程

### 3.1 基础设施层问题

#### 问题：AI 生成的图片在部署后丢失

**发现方式**：用户反馈课程页面图片不显示。

**根因**：AI 生成的图片存储在 `public/ai-images/` 目录下（部署目录内）。CI/CD 使用 `rsync --delete` 同步代码，每次部署都会删除服务器上有但 git 中没有的文件。

**修复**：将图片存储目录移到部署目录外（`/opt/aidash/uploads/ai-images/`），通过环境变量 `AI_IMAGES_DIR` 配置。

**推广经验**：
- 运行时生成的数据（图片、上传文件、日志）绝不能放在代码部署目录内
- 部署脚本的 `--delete` 标志会清除所有非版本控制的文件
- 应建立"代码目录"和"数据目录"的明确分离

#### 问题：课次生成被截断

**发现方式**：部分课次生成失败，日志显示"AI 输出解析失败"。

**根因**：`maxTokens: 4096` 对内容较多的课次不够（有些课次需要 5000+ token），AI 输出在 JSON 中间被截断，导致 JSON 解析失败。

**修复**：`maxTokens` 从 4096 提升到 16384。

**推广经验**：
- AI 输出的 token 上限必须根据实际输出量设定，留足余量
- 结构化输出（JSON）被截断后无法解析，比纯文本截断更严重
- 应该监控 `outputTokens / maxTokens` 的比例，接近 100% 时告警

### 3.2 Prompt 组装层问题

#### 问题：图片修改意见不断累积

**发现方式**：用户反馈多次修改图片后，画面元素越来越偏离主题。

**根因**：每次修改图片时，系统把"原始 prompt + 本次反馈"拼接后的结果存回 `promptField`。下次修改时读取的"原始 prompt"已经包含了上次的反馈。多次修改后 prompt 越来越长，历史指令互相冲突。

```
第1次修改：原始prompt + "加一只兔子"  → 存回
第2次修改：(原始prompt + "加一只兔子") + "换成水彩风"  → 存回
第3次修改：((原始prompt + "加一只兔子") + "换成水彩风") + "色调暖一些"  → ...
```

**修复**：修改图片时只用原始 prompt + 当次反馈拼接生成，不把拼接结果存回 `promptField`。原始 prompt 始终保持不变。

**推广经验**：
- 区分"生成用的临时 prompt"和"持久化存储的 prompt"
- 持久化的应该是"原始意图"，不是"累积指令"
- 增量修改模式（delta）比覆盖模式（overwrite）更安全

#### 问题：图片链路缺少构图引导、年龄提示

**发现方式**：系统性核查所有图片生成链路后发现。

**根因**：项目中有 4 条图片生成链路（首次生成、重新生成、修改图片、封面生成），但只有首次生成加了构图引导。年龄提示只有封面生成加了。其他链路遗漏。

| 链路 | 构图引导 | 年龄提示 | 风格前缀 |
|------|:---:|:---:|:---:|
| 首次生成 | ✓ | ✗ | ✓ |
| 重新生成 | ✗ | ✗ | ✓ |
| 修改图片 | ✗ | ✗ | ✓ |
| 封面生成 | ✗ | ✓ | ✓ |

**修复**：统一所有链路的 prompt 拼接逻辑：`构图引导 + 年龄提示 + 风格前缀 + 内容描述`。并区分课次标题图（需要构图引导）和课程包封面（不需要构图引导）。

**推广经验**：
- 多条链路做同一件事时，prompt 的组装逻辑必须统一
- 新增一条链路时，必须对照已有链路检查是否遗漏了某个 prompt 层次
- 用一个清单列出"每条链路应该包含哪些 prompt 组件"，每次变更后核查

#### 问题：封面图错误使用课次构图引导

**发现方式**：审查生产环境的 prompt 审计日志。

**根因**：课程包封面生成时复制了课次标题图的构图引导代码（"元素集中在画面中央水平带状区域"），但封面图的显示场景和课次标题图完全不同，这个约束导致封面图构图不自然。

**修复**：封面图生成去掉构图引导。

**推广经验**：
- 不要盲目复用 prompt 组件，每个组件要明确"适用于哪些场景"
- Preset/配置要有清晰的命名和分类，避免"通用"组件被误用到不适合的场景

### 3.3 模板系统层问题

#### 问题：DB 模板存在时基线不注入

**发现方式**：全面核查模板内容后发现。

**根因**：代码逻辑是：
```typescript
const dbPrompt = await getSystemPrompt(actionKey, templateCtx);
const systemPrompt = dbPrompt ?? (getBaselinePrompt() + hardcodedPrompt());
```

DB 模板存在时用 DB 模板（无基线），不存在时用硬编码回退（有基线）。但 DB 模板中没有 `{{通用基线}}` 等变量——种子数据直接搬了硬编码文本，没有做变量化改造。

**修复**：在 DB 模板中追加基线变量区：
```
# 课程设计基线（请严格遵循）
{{通用基线}}
{{年龄段基线}}
{{级别基线}}
{{组织形态基线}}
{{产出物基线}}
{{分层规则矩阵}}
```

**推广经验**：
- 模板系统和硬编码回退的行为必须一致，不能"模板生效时少了什么"
- 基线注入应该是模板的责任（模板决定注入什么），而不是代码的责任（代码无条件注入）
- 种子数据不是"把硬编码复制进去"，而是"按模板系统的规范重新设计"

#### 问题：硬编码基线加载函数在生产环境返回空

**发现方式**：审查 validate_lesson 的 prompt 日志发现没有基线内容。

**根因**：`getBaselinePrompt()` 从文件系统读取 `课程设计基线文档_v2.md`，但基线文档已经拆分为 23 个维度文件，旧文件名不存在了。函数 fallback 返回空字符串。

**修复**：不再依赖文件系统基线，全部通过 DB 模板的变量注入。新增 `validate_lesson` 种子模板。

**推广经验**：
- 硬编码回退路径也需要定期验证，不能"写了就忘"
- 文件系统依赖（读文件、读配置）在部署环境中可能和开发环境不一致
- 最终目标是让所有 prompt 都走模板系统，硬编码只作为"从未配置过模板"时的兜底

#### 问题：generate-cover 完全绕过模板系统

**发现方式**：全面核查 7 条 AI 调用链路。

**根因**：封面图生成路由是早期写的，直接硬编码英文 prompt，没有调用 `getSystemPrompt()`，没有注入基线，没有模板变量替换。

**修复**：
1. 新增 `resolveLightPrompt()`（轻量模板解析，只做变量替换，不注入基线）
2. 封面图路由接入模板系统
3. 种子数据新增 `package_cover` 模板

**推广经验**：
- 文本 prompt 和图片 prompt 都应该走模板系统，只是注入的内容不同
- 建立"模板系统接入检查清单"，新增 AI 调用路由时必须确认接入

#### 问题：模板变量替换为"未指定"

**发现方式**：生产环境生成封面后检查 prompt 日志。

**根因**：
1. 项目 `imageStylePrompt` 为 null → 模板引擎 `str(null)` 返回 "未指定"
2. 项目 `ageRange` 为旧格式 "8-12"（不是 "A2"）→ BaselineDoc 查不到标签 → 返回 "未指定"

**修复**：这是数据兼容性问题，旧格式项目后续不再产生。新项目使用标准代号（A1-A4），变量替换正常。

**推广经验**：
- 模板变量的"未指定"默认值不总是合适的——对图片模型来说，"未指定"这个中文字会干扰生成
- 考虑对不同场景使用不同的 null 处理策略（空字符串 vs "未指定" vs 默认值）
- 数据格式升级时，需要考虑旧数据和新模板的兼容性

### 3.4 前端交互层问题

#### 问题：封面弹窗默认提示词绕过模板系统

**发现方式**：用户反馈重新生成的封面和课程主题无关。

**根因**：`CoverRegenerateModal` 预填了一段硬编码中文提示词（"色彩丰富、有吸引力的儿童教育课程封面插画..."）。用户不修改直接提交时，这段文字作为 `customPrompt` 传给后端，走了 `customPrompt` 分支——完全绕过 DB 模板，也不包含课程标题、方向等项目信息。

**修复**：弹窗改为空文本框 + 引导文案（"描述您想要的封面效果"）。用户留空直接提交走模板分支，填了内容则拼接在模板之后。

**推广经验**：
- 前端的"默认值"可能绕过后端的模板系统，形成隐蔽的 prompt 旁路
- 前端不应该持有 prompt 内容，prompt 的组装权应该完全在后端
- 前端只提供"用户的补充意见"，不提供"基础 prompt"

### 3.5 种子数据管理问题

#### 问题：种子脚本覆盖管理员修改

**发现方式**：每次运行种子脚本后，管理员在后台手动修改的模板被重置。

**根因**：种子脚本使用 `upsert`（`update + create`），每次运行都用种子中的内容覆盖 DB 中的内容。

**修复**：改为"只创建不更新"——`findUnique` 检查是否存在，存在则跳过。

**推广经验**：
- 种子数据是"初始化"用的，不是"强制重置"用的
- 如果需要强制更新，应该提供单独的 `--force` 参数
- 管理员在后台修改的配置是"运行时数据"，不应该被代码部署覆盖

## 四、最终架构设计

### 4.1 Prompt 组装分层模型

```
┌─────────────────────────────────────────────┐
│              最终 Prompt                      │
├─────────────────────────────────────────────┤
│ 第1层：模板指令（DB 模板 or 硬编码回退）       │
│   ↑ 变量替换：{{项目标题}} {{课程方向}} 等      │
│   ↑ 基线注入：{{通用基线}} {{年龄段基线}} 等    │
├─────────────────────────────────────────────┤
│ 第2层：用户消息（代码拼接）                    │
│   项目属性 + 当前内容 + 用户反馈              │
├─────────────────────────────────────────────┤
│ 第3层：图片附加层（仅图片生成）               │
│   构图引导 + 年龄提示 + 风格前缀              │
└─────────────────────────────────────────────┘
```

### 4.2 模板系统三层架构

| 层次 | 职责 | 谁控制 |
|------|------|--------|
| DB 模板 | 指令内容 + 基线注入 | 管理员在后台配置 |
| 硬编码回退 | DB 无模板时的默认行为 | 开发者在代码中维护 |
| 种子数据 | 初始化 DB 模板 | 只创建不覆盖 |

### 4.3 模板类型区分

| 类型 | 函数 | 基线注入 | 用途 |
|------|------|:---:|------|
| 文本模板 | `getSystemPrompt()` | ✓ | 文本 AI 的 system prompt |
| 轻量模板 | `resolveLightPrompt()` | ✗ | 图片 prompt、标题生成等 |

### 4.4 Prompt 审计体系

每次 AI 调用记录到 `CourseRndAiCallLog`：
- `promptLog`：完整的 system prompt（模板 + 基线 + 变量替换后的最终结果）
- `messageLog`：完整的 user message
- 管理端"AI 调用记录"页面可查看每次调用的完整 prompt

## 五、检查清单

### 新增 AI 调用路由时

- [ ] 是否接入模板系统（`getSystemPrompt` 或 `resolveLightPrompt`）？
- [ ] TemplateContext 是否传入了所有必要的项目属性？
- [ ] 用户消息是否包含了完整的项目上下文？
- [ ] 硬编码回退 prompt 是否和 DB 模板行为一致？
- [ ] 是否记录了 prompt 审计日志（`promptLog` + `messageLog`）？
- [ ] 是否在种子数据中添加了对应的模板？

### 图片生成链路

- [ ] 是否加了年龄提示？
- [ ] 是否加了风格前缀（`imageStylePrompt`）？
- [ ] 是否加了构图引导（仅课次标题图）？
- [ ] 修改图片时是否保留原始 prompt 不累积？
- [ ] 不同链路的 prompt 组装是否一致？

### 模板变量

- [ ] 模板中使用的变量是否都在 `buildVariableMap` 中定义？
- [ ] `null` 值的处理是否合理（"未指定" vs 空字符串 vs 默认值）？
- [ ] 图片模板中的变量（如年龄段）是否对图片模型有意义？

### 种子数据

- [ ] 新增模板是否只创建不覆盖？
- [ ] 模板内容是否包含了必要的基线变量？
- [ ] 模板是否经过生产环境验证（检查 prompt 审计日志）？

### 部署

- [ ] 运行时生成的文件（图片、上传）是否在部署目录外？
- [ ] 环境变量是否配置了数据目录路径？
- [ ] 部署后是否需要运行种子脚本？（只有新增模板时需要）

## 六、适用于其他 AIGC 业务的通用原则

1. **Prompt 是产品，不是代码** — 它需要版本管理、配置化、可审计，和代码分离
2. **看 AI 收到了什么，而不是你写了什么** — 建立 prompt 审计日志
3. **多条链路做同一件事时，统一 prompt 组装逻辑** — 一处改，处处改
4. **图片 prompt 和文本 prompt 同等重视** — 图片更容易出错但更难发现
5. **前端不持有 prompt，只提供用户意图** — prompt 组装权在后端
6. **运行时数据和代码分离** — 图片、模板、配置不能放在部署目录
7. **种子数据是初始化，不是强制重置** — 保护管理员的运行时修改
8. **硬编码回退也需要验证** — 文件改名、路径变更都可能让回退失效
9. **变量替换不等于"替换了就对"** — "未指定"可能比不替换更糟糕
10. **AIGC 的 bug 是隐性的** — 需要主动核查，不能等用户发现
